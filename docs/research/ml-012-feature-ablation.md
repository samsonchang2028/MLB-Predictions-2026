# ML-012: Feature-family ablation study

Status: complete. Research/analysis only -- no change to the ADR-006 locked
production model, its features, or its hyperparameters.

Machine-readable report: `reports/experiments/ml-012-feature-ablation.json`
(generated by `scripts/ml012_feature_ablation.py`, build `a910017bac839af5`,
`random_state=0`).

## 1. Goal

Determine which Gold feature families actually improve out-of-sample
probability quality for the ADR-006 locked XGBoost model, using the existing
ML-004 walk-forward framework, and produce KEEP / INVESTIGATE / REMOVE
verdicts.

## 2. Feature-family taxonomy (real, not invented)

`features/build.py`'s `_COMPONENTS = ("team", "starter", "bullpen")` names
every Gold column as `home_/away_/diff_{component}_{key}`. The existing
FEAT-006 completeness gate (`features/completeness.py`,
`REQUIRED_FAMILY_COLUMNS`) already refines this into the grouping this study
reuses verbatim (no new taxonomy was invented for ML-012):

| Family | Columns (certified build) | What it covers |
|---|---|---|
| `team` | 84 | Team win%, runs scored/allowed, run differential, over `before` (season-to-date) and `L7`/`L14`/`L30` rolling windows, home/away/diff |
| `starter` | 75 | Probable/actual starter identity + season and rolling (`L3`/`L5`/`L10`) ERA/WHIP/K-rate/BB-rate/IP-per-start |
| `bullpen` | 45 | Team bullpen ERA/WHIP/IP/appearances over `L7`/`L14`/`L30` |
| `rest_schedule` | 36 | Cross-component fatigue/rest: starter `days_rest` + previous-start workload, and bullpen usage in the prior 1/3 days |

84 + 75 + 45 + 36 = 240 = the certified build's full feature-column count,
with zero leftover/unclassified columns -- confirmed both by inspecting
`reports/data-quality/gold-completeness-a910017bac839af5.json` directly and
by `experiments.ablation.family_columns`, which raises loudly instead of
silently dropping a column if this taxonomy ever stops covering the whole
build. Full column lists per family are in
`reports/experiments/ml-012-feature-ablation.json:families`.

Note `rest_schedule`'s bullpen columns (`bullpen_*_prior_1d/3d`) and the
`bullpen` family's own columns (`bullpen_*_L7/L14/L30`) both describe recent
bullpen workload, just over different windows -- this overlap turns out to
matter (see Section 5).

## 3. Experiment design

Both ablation styles were run (family count is small enough -- 4 -- that
running both is cheap and each answers a different question; this is the
ML-012 "implementer's choice" documented per the task):

- **Leave-one-group-out**: `full` model vs. `full minus family`, for each of
  the 4 families. Answers "does removing this family hurt?"
- **Incremental**: `team -> +starter -> +bullpen -> +rest_schedule (=full)`.
  Answers "how much does each addition help over what came before?"

**Primary model**: the ADR-006 **locked** tuned XGBoost
(`max_depth=2, learning_rate=0.03, n_estimators=300, reg_lambda=10.0,
min_child_weight=3.0, subsample=0.8, colsample_bytree=0.8`), hardcoded from
the accepted ADR and never retuned by this study
(`experiments.ablation.ADR006_XGBOOST_PARAMS`). Run across all three ADR-003
window strategies: expanding, rolling_2, rolling_3.

**Sanity checks**: logistic regression and random forest, leave-one-out only,
expanding window only (per task scope: "not a new comparison project").

**Framework reuse**: every fold comes from `evaluation.splits.expanding_folds`
/ `rolling_folds` unmodified; every metric comes from
`evaluation.runner.run_evaluation` unmodified (log loss, Brier, ECE, secondary
ROC-AUC/accuracy via `_probability_metrics`, exactly as ML-005/006/007/008
already use it). No new fold logic, no new metric math, no new model code was
written. As a direct correctness check: the `leave_one_out:full` / expanding
row reproduces ADR-006's own tuning-pass evidence exactly (log loss
`0.68124`, Brier `0.24408`, ECE `0.01578`, ROC-AUC `0.58446`, accuracy
`0.56396`, n=9,694) -- the harness is not silently drifting from the numbers
already on record.

**Column-subset mechanism**: an ablation variant is produced by filtering
each row's `features` dict to a column subset (`experiments.ablation._subset_matrix`).
The build's original `feature_completeness` PASS report and `build_id` are
carried through unchanged rather than recomputed against the narrowed subset,
per the task's "reuse the already-completeness-gated build" constraint --
recomputing completeness against a deliberately-narrowed column set would
produce a meaningless FAIL, not a real data-quality signal.

**Pooled metrics**: `variant_aggregates` uses `run_evaluation`'s own
`report["aggregate"]` (pooled via `_probability_metrics` over concatenated
fold predictions) rather than averaging per-fold ECE, because ECE is a
nonlinear binned statistic and an n-weighted average of per-fold ECE is not
the same number as the true pooled ECE (log loss and Brier, being simple
per-sample means, are unaffected by this distinction and match either way).

**2026 holdout**: never read. Folds structurally exclude it
(`evaluation.splits.HOLDOUT_SEASON`); `experiments.ablation._assert_no_holdout`
additionally asserts no produced fold-metric row ever carries
`test_season == 2026` or a 2026 training season, mirroring
`experiments.comparison._assert_no_holdout`'s existing pattern.

## 4. Redundancy / leakage review

**Manual review**: every feature family is produced by an already
leakage-tested point-in-time builder (`FEAT-002` starter, `FEAT-003` bullpen,
team features, all covered by `tests/leakage/`), assembled by `FEAT-004`'s
`build_feature_matrix`, which isolates `home_win` into `row["target"]` only
and never into `row["features"]`. No column name in the 240-column list
resembles a postgame/result-derived quantity (no `score`, `result`, `win`,
`runs_this_game`, etc. among the team/starter/bullpen/rest_schedule columns
above -- everything is `_before`/`_L{n}`/`_prior_{n}d`, i.e. explicitly prior
to the game being predicted).

**Empirical scan**: `experiments.ablation._univariate_leakage_scan` computes
each column's univariate ROC-AUC against the label over all 12,118 labeled
development rows (2026 asserted absent; the scan raises if it ever sees a
2026 row). In this repo's demonstrably weak-signal domain (the best full
multi-feature model tops out at ROC-AUC ~0.584), a single column clearing
0.65 AUC alone would be a strong leakage smell. **Result: 0 columns flagged.**
The strongest univariate columns are exactly the ones domain knowledge
predicts (`diff_team_run_diff_total_before` at 0.5801, `diff_team_wins_before`
at 0.5793, `diff_team_win_pct_before` at 0.5754, ...) -- cumulative
team-quality differentials, topping out barely above the full model's own
AUC, not suspiciously far above it.

**Verdict: no leakage found.** Ablation results below are interpreted as
valid; this is not a P0/P1 finding.

## 5. Results

### 5.1 Leave-one-group-out (pooled log loss / Brier / ECE / AUC)

|---|---|---|---|---|---|---|
| expanding | **full** | 0.68124 | 0.24408 | 0.01578 | 0.58446 | 9,694 |
| expanding | minus team | 0.68443 | 0.24564 | 0.02039 | 0.57359 | 9,694 |
| expanding | minus starter | 0.68369 | 0.24528 | 0.01962 | 0.57561 | 9,694 |
| expanding | minus bullpen | 0.68229 | 0.24456 | 0.01713 | 0.58175 | 9,694 |
| expanding | minus rest_schedule | 0.68303 | 0.24494 | 0.02238 | 0.57908 | 9,694 |
| rolling_2 | **full** | 0.68432 | 0.24565 | 0.02674 | 0.57172 | 4,847 |
| rolling_2 | minus team | 0.68659 | 0.24674 | 0.02721 | 0.56215 | 4,847 |
| rolling_2 | minus starter | 0.68600 | 0.24641 | 0.02439 | 0.56624 | 4,847 |
| rolling_2 | minus bullpen | 0.68533 | 0.24614 | 0.02485 | 0.56863 | 4,847 |
| rolling_2 | minus rest_schedule | 0.68519 | 0.24610 | 0.03005 | 0.56762 | 4,847 |
| rolling_3 | **full** | 0.68240 | 0.24471 | 0.02376 | 0.57656 | 4,847 |
| rolling_3 | minus team | 0.68502 | 0.24596 | 0.02010 | 0.56844 | 4,847 |
| rolling_3 | minus starter | 0.68438 | 0.24562 | 0.02140 | 0.57048 | 4,847 |
| rolling_3 | minus bullpen | 0.68367 | 0.24535 | 0.02281 | 0.57241 | 4,847 |
| rolling_3 | minus rest_schedule | 0.68317 | 0.24510 | 0.02428 | 0.57390 | 4,847 |

Log-loss cost of removing each family (higher = more valuable; `full` minus
that row, positive means removal hurts):

| Family removed | expanding | rolling_2 | rolling_3 | consistent direction? |
|---|---|---|---|---|
| team | +0.00319 | +0.00227 | +0.00262 | yes -- always the biggest loss |
| starter | +0.00245 | +0.00168 | +0.00198 | yes -- always 2nd biggest loss |
| bullpen | +0.00105 | +0.00101 | +0.00127 | yes -- always the 3rd or 4th, small |
| rest_schedule | +0.00179 | +0.00087 | +0.00077 | rank flips vs. bullpen between windows |

Every family's removal increases log loss in every window (no family
improves the model by being removed), but the effect sizes are very unequal:
team and starter are 2-4x larger than bullpen/rest_schedule, consistently,
across all three windows. ECE does not move consistently with any family's
removal (e.g. removing `team` *improves* ECE in rolling_3 but *worsens* it in
expanding) -- expected, since ADR-006 locks the model uncalibrated and ECE is
explicitly secondary to log loss/Brier per ADR-003.

### 5.2 Incremental (expanding window, the ADR-006-selected window)

| Variant | log loss | Brier | ECE | ROC-AUC |
|---|---|---|---|---|
| team | 0.68696 | 0.24681 | 0.02067 | 0.56505 |
| team + starter | 0.68253 | 0.24469 | 0.01990 | 0.58059 |
| team + starter + bullpen | 0.68303 | 0.24494 | 0.02238 | 0.57908 |
| team + starter + bullpen + rest_schedule (= full) | 0.68124 | 0.24408 | 0.01578 | 0.58446 |

Adding `starter` on top of `team` is the single largest improvement of any
step (log loss -0.00443, AUC +0.0155). Adding `bullpen` on top of
`team+starter` makes log loss *slightly worse* (+0.00050) and AUC slightly
worse (-0.0015), even though the leave-one-out view above shows bullpen has a
small *positive* marginal value when removed from the full model. This is not
a contradiction in the harness (both numbers reproduce cleanly and
deterministically) -- it is evidence that bullpen's information is partly
redundant with what `rest_schedule` (added last, added interacting with
`bullpen`) already encodes, since `rest_schedule` explicitly includes recent
bullpen usage columns (`bullpen_*_prior_1d/3d`) alongside the plain `bullpen`
family's own `bullpen_*_L7/L14/L30` usage columns (Section 2). Adding
`rest_schedule` last recovers the full model's best numbers.

### 5.3 Sanity checks (logistic regression / random forest, expanding, leave-one-out)

| Model | Variant | log loss | Brier | ECE |
|---|---|---|---|---|
| logistic_regression | full | 0.70311 | 0.25243 | 0.05290 |
| logistic_regression | minus team | 0.70130 | 0.25222 | 0.04734 |
| logistic_regression | minus starter | 0.69640 | 0.24985 | 0.04265 |
| logistic_regression | minus bullpen | 0.70117 | 0.25162 | 0.04720 |
| logistic_regression | minus rest_schedule | 0.69777 | 0.25042 | 0.04570 |
| random_forest | full | 0.68593 | 0.24628 | 0.01986 |
| random_forest | minus team | 0.68869 | 0.24770 | 0.02705 |
| random_forest | minus starter | 0.68980 | 0.24824 | 0.02819 |
| random_forest | minus bullpen | 0.68739 | 0.24694 | 0.02761 |
| random_forest | minus rest_schedule | 0.68814 | 0.24737 | 0.02965 |

Random forest agrees directionally with XGBoost: `full` beats every
leave-one-out variant. Logistic regression is the outlier -- it is *better*
without `starter` or `rest_schedule` than with the full column set
(uncalibrated 240-column logistic regression is known from ML-005/006 to be a
weaker overall candidate than XGBoost; a raw, unregularized linear model with
75+36 extra noisy/collinear starter and rest columns can plausibly overfit
where a shallow, heavily-regularized tree ensemble does not). This is
consistent with ADR-006 already rejecting logistic regression for XGBoost and
does not change this study's XGBoost-based verdicts; it is reported as
context, not used for selection (sanity-check-only scope).

## 6. KEEP / INVESTIGATE / REMOVE verdicts

| Family | Verdict | Why |
|---|---|---|
| **team** | **KEEP** | Largest, most consistent log-loss contribution in every window and both ablation methods (leave-one-out and incremental); matches the domain prior that recent team form/run-differential is a core moneyline signal; also the single strongest univariate-AUC family (Section 4). |
| **starter** | **KEEP** | Second-largest, most consistent contribution in every window; the single biggest incremental improvement step of the whole study (team -> team+starter). Matches the well-established baseball prior that the starting-pitcher matchup materially moves win probability. |
| **bullpen** | **INVESTIGATE** | Small, consistently-positive marginal value when removed from the full model, but near-zero-to-negative value in the incremental view once `rest_schedule` is present later in the sequence (Section 5.2). Overlaps in content with `rest_schedule`'s bullpen-usage columns (Section 2). Not a REMOVE candidate (removing it never improves the model in any window/method tested), but the current team-aggregate `L7/L14/L30` bullpen ERA/WHIP framing may be too coarse to add information beyond what `rest_schedule`'s recent-workload columns already capture -- a per-reliever refinement (Section 7, recommendation #3) is a more targeted next step than either keeping or dropping the family as-is. |
| **rest_schedule** | **INVESTIGATE** | Moderate, but its rank relative to `bullpen` flips between the expanding window (rest_schedule > bullpen) and both rolling windows (bullpen > rest_schedule) -- not the noise-free monotonic pattern `team`/`starter` show. ECE effect is inconsistent in direction. Same redundancy concern as `bullpen` (Section 2): worth a follow-up specifically aimed at whether `rest_schedule`'s bullpen-usage columns and the `bullpen` family's own usage columns can be consolidated without losing the fatigue-specific signal, rather than treated as two separate families that partially duplicate each other. |

No family qualifies for REMOVE: removing any family increases log loss in
every window and both ablation methods tested, so this study finds no
evidence that any current family actively hurts the ADR-006 locked model.

## 7. Top-3 ranked candidate future feature additions

Ranked by likely predictive value, temporal-data availability, engineering
effort, leakage risk, and maintainability (brief justification, not a full
spec; this ranking is informational, not a selection -- any future addition
requires its own task and does not touch ADR-006):

1. **Park factors** (season-level static run/HR environment adjustment per
   venue). Highest effort/risk/value ratio of the three: park factors are
   published, stable within a season, and trivially point-in-time safe
   (known well before any game at that park is played, no per-game timing
   discipline required unlike odds/lineups). Cheapest and safest of the
   candidates the task's own suggestion list names (park factors, weather,
   handedness/matchup, bullpen availability, confirmed lineups, umpire data).

2. **Handedness/platoon matchup splits** (team-vs-probable-starter-handedness
   split stats, e.g. team wOBA/win rate vs. LHP vs. RHP). Well-documented
   sabermetric signal with a plausible incremental lift over the existing
   team/starter families' handedness-blind aggregates. Feasible because the
   probable starter's identity/handedness is already ingested by the existing
   `FEAT-002` starter builder -- this is a natural extension of an existing
   point-in-time-safe pipeline, not a new ingestion source, keeping leakage
   risk low (same pregame-availability discipline already proven out for
   starter features).

3. **Per-pitcher bullpen availability/fatigue** (reliever-level recent-usage
   flags rather than the current team-aggregate `bullpen`/`rest_schedule`
   framing). Directly targets this study's own INVESTIGATE finding for
   `bullpen`/`rest_schedule` (Section 6): if the current team-aggregate
   bullpen signal is muted by redundancy between the two families, a
   per-reliever "is this team's best reliever unavailable today" feature may
   carry information the aggregates wash out. Cheapest of the three to
   engineer (reuses the already-ingested `silver.pitcher_appearances` data
   FEAT-003 already builds from -- no new external source), and inherits
   FEAT-003's existing leakage-tested point-in-time discipline directly.

Runners-up not in the top 3, for completeness: **confirmed starting lineups**
(potentially higher value than platoon splits alone, but meaningfully higher
leakage risk -- requires a new real-time confirmation feed and strict
prediction-cutoff timing discipline analogous to ADR-002's odds-snapshot
rules -- and higher ongoing engineering/maintenance cost); **weather**
(uncertain win-probability value vs. run-total value, requires a new external
forecast-vs-actual-timestamp discipline); **umpire assignment** (modest,
better suited to a totals/run-environment model than moneyline).

## 8. Known limitations

- The leave-one-out and incremental ablation methods can disagree on a
  family's marginal value when families are informationally redundant
  (Section 5.2, bullpen); this is reported as a finding (motivating the
  per-family INVESTIGATE verdicts and recommendation #3), not resolved by
  this study.
- The univariate leakage scan (Section 4) only screens single-column
  predictive strength; it cannot detect multi-column combinations that leak
  only jointly. The manual review (column-name/provenance inspection plus
  the existing point-in-time-tested builders) is the primary safeguard for
  that gap.
- Sanity-check models (logistic, random forest) only ran the expanding window
  with leave-one-out, not the full 3-window x 2-method matrix run for
  XGBoost, per the task's explicit "not a new comparison project" scope.
- All effect sizes here are small in absolute terms (fractions of a
  thousandth to a few thousandths of log loss) -- consistent with the
  already-documented weak overall edge of the V1 model
  (`reports/experiments/v1-model-diagnostics.json`), not a sign that this
  study's methodology is broken.
