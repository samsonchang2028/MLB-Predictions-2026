# ML-015: Prospective model and market diagnostic study

Status: complete. Diagnostic/monitoring only -- no change to the ADR-006
locked production model, its features, its hyperparameters, its calibration,
or the `src/app/board.py` PLAY/PASS threshold.

Machine-readable report:
`reports/experiments/ml-015-prospective-diagnostic.json` (generated by
`scripts/ml015_prospective_diagnostic.py`, reading the live
`state/predictions/` journal -- real production predictions, not a
backtest).

## 1. Goal

The live dashboard reported roughly a 39% PLAY win rate over the first ~50-60
finished plays of real, prospective (not backtested) production predictions.
This study determines whether that shortfall traces to (1) probability-model
performance, (2) market disagreement/edge calculation, (3) PLAY selection
behavior, (4) small-sample variance, or (5) a specific failure regime --
without retuning, recalibrating, or otherwise touching the locked V1 model.

**Three-system distinction** (see `src/app/board.py`'s own module
docstring): probability model (raw `model_probability` = P(home_win)) vs.
market engine (`model_probability - market_probability` = edge) vs. betting
selection layer (PLAY/PASS, a synthetic **display-only** threshold,
`DEFAULT_EDGE_THRESHOLD = 0.02`). This report keeps the three separate
throughout and does not blame "bad model calibration" for a PLAY shortfall
unless Part 1/3 evidence (not just Part 2) supports it.

## 2. Methodology

**Data.** The real OBS-001/OBS-002 prediction journal as of report
generation: `state/predictions/daily.jsonl` (immutable PIPE-001 prediction
records), `state/predictions/journal.jsonl` (OBS-001 result-enrichment
records, joined by `(game_pk, prediction_timestamp)`), plus
`game_features.jsonl` (per-game feature breakdown, PIPE-004) and
`skipped.jsonl` (games withheld pre-prediction for a missing starter).
`state/predictions/` is gitignored local/homelab runtime data; this study
reads it read-only from the main checkout, never writing to it.

**Row assembly.** Reuses `app.board.load_daily_board_with_diagnostics`
end-to-end -- the exact same latest-prediction-per-game dedup, journal join,
PLAY/PASS labeling (`DEFAULT_EDGE_THRESHOLD`), and selected-side probability
computation (`model_chance`/`market_chance`) the live dashboard itself uses.
This module never redefines that join, dedup, or threshold logic. Raw
American odds and time-to-first-pitch (fields the board's display shape
omits) are joined back to the same `(game_pk, prediction_timestamp)` key from
the raw `daily.jsonl` record.

**Metrics.** `evaluation.runner._probability_metrics` (log loss, Brier, ECE,
ROC-AUC, accuracy) -- the identical formulas ADR-003 and the 2026 holdout
report already use. Parts 1/3/5 use the raw P(home_win) framing (directly
comparable to the holdout and to ML-013); Parts 2/4 use the selected-side
framing (PLAY/PASS and edge are about the picked side, not the raw home-win
call).

**Failure regimes.** Reuses `experiments.failure_regimes.slice_by` /
`feature_value_by_game_pk` / `tercile_labels` verbatim (ML-013's slicing
machinery), so bucket/tercile conventions match ML-013's development-fold
report where the concept overlaps.

**No ROI.** Neither `daily.jsonl` nor the OBS-001 journal record a
stake/wager amount (same finding `app.performance.MARKET_RELATIVE_NOTE`
already documents for the performance dashboard); every ROI field in the
report is `null` with a stated reason rather than a fabricated number.

**2026 holdout.** Read only by `historical_comparison`, a separate function
called *after* every prospective-sample computation is already complete --
`build_report` (Parts 1-5) has no holdout parameter at all and cannot
structurally depend on holdout values. Comparison-only, never a selection
input. Tested explicitly (`test_build_report_never_accepts_holdout_data`,
`test_historical_comparison_is_read_only_and_does_not_mutate_part1`).

## 3. Sample size

**N = 94 resolved eligible predictions** (one row per `game_pk`, the latest
prediction before first pitch, joined to a Final result) as of this report's
generation. The raw `daily.jsonl` file has more rows (some games were
predicted twice -- once ahead of the slate, once closer to first pitch, as
odds/features refreshed); those are correctly deduped to one row per game,
not double-counted. 5 additional games were withheld entirely upstream for
no announced starter (`skipped.jsonl`), never reaching a prediction row. 0
malformed/skipped board rows.

This is a small sample. Per ADR-003/ML-013 convention (`LOW_N_THRESHOLD =
30`), every slice below n=30 is flagged `low_confidence` in the machine
report rather than omitted or overstated -- most bucket/regime rows below
are low-confidence. Read every number below together with its N.

## 4. Part 1 -- all resolved eligible predictions (raw P(home_win))

| metric | prospective (n=94) | 2026 holdout (n=1,797) | delta |
|---|---|---|---|
| log loss | 0.7012 | 0.6888 | +0.0125 |
| Brier | 0.2537 | 0.2478 | +0.0059 |
| ECE (10-bin) | 0.1339 | 0.0222 | +0.1116 |
| ROC-AUC | 0.5473 | 0.5497 | **-0.0024** |
| accuracy | 0.5851 | 0.5381 | +0.0470 |
| avg predicted home probability | 0.5150 | -- | -- |
| actual home-win rate | 0.4681 | -- | -- |
| calibration gap (scalar, \|avg p - actual rate\|) | 0.0469 | -- | -- |

**Read this as: the model's core discrimination is intact.** ROC-AUC is
within 0.0024 of the locked holdout value -- essentially identical, well
inside sampling noise at n=94. Log loss and Brier are modestly worse (+0.012
/ +0.006), a gap comparable in magnitude to the already-documented
dev-to-holdout degradation from ML-011 (+0.0075 log loss), not a new or
larger regression. Accuracy is actually *higher* than holdout (secondary
metric, not primary; noisy at this N). The scalar calibration gap (0.047) is
unremarkable for n=94.

The 10-bin ECE (0.1339) looks alarming next to holdout's 0.0222, but this is
binning noise, not a real calibration collapse: with 94 rows spread over 10
equal-width bins, several bins hold single digits of games (see Part 3, all
`low_confidence`), and ECE is known to be unstable at this density. The
scalar calibration gap above is a more trustworthy single number at this N,
and it is not alarming.

**Conclusion for Part 1 alone: no evidence of a core model-probability
regression.** The interesting signal is elsewhere (Part 2/4/5, below).

## 5. Part 2 -- PLAY subset

| | value | N |
|---|---|---|
| PLAY rows | 68 | 68 of 94 (72%) |
| wins / losses | 30 / 38 | |
| win rate | **44.1%** | 68 |
| avg model P(selected side) | 52.5% | 68 |
| actual selected-side win rate | 44.1% | 68 |
| avg market P(selected side) | 46.3% | 68 |
| avg \|edge\| | 6.1 pts | 68 |
| avg selected-side American odds | +42 | 68 |
| model-vs-actual gap | 8.3 pts (model overconfident) | 68 |
| ROI | not computed (no stake field; see below) | -- |

The live dashboard's originally-cited ~39% has since drifted to 44.1% as
more of the sample resolved -- both figures are within normal small-sample
variance of each other (n=68), not a meaningful revision.

**The interesting comparison is against Part 1's raw accuracy.** Simply
following the model's raw favorite on *every* resolved game (all 94, no
selection) would have gone 58.5%. The actual PLAY selections -- the subset
the edge/selection layer specifically chose as its *highest-confidence,
market-disagreement* picks -- won only 44.1% of a smaller, cherry-picked
subset. A selection mechanism that underperforms simply "always take the raw
favorite" over the same window, on the games it chose to highlight, is a
selection-layer/market-disagreement signal, not (by itself) evidence the
underlying probability model is broken -- Part 1's raw metrics for the exact
same period look fine.

Model-vs-actual gap (avg model P(selected side) 52.5% vs. actual 44.1%,
n=68) is an 8.3-point overconfidence gap on the selected side specifically.
At n=68 this is suggestive, not proof, but it lines up with the edge-bucket
finding in Part 4.

**No stake/wager amount is recorded anywhere in `daily.jsonl` or the OBS-001
journal** (confirmed by inspecting both schemas directly, consistent with
`app.performance.MARKET_RELATIVE_NOTE`'s existing repo-wide finding for the
performance dashboard) -- ROI is reported as `null` with that reason rather
than fabricated from an assumed flat-stake convention.

## 7. Part 4 -- edge buckets (selected-side, \|model - market\| magnitude)

| bucket | n | avg model P(side) | avg market P(side) | actual win rate | low-N |
|---|---|---|---|---|---|
| 0-2% | 26 | 0.484 | 0.474 | **65.4%** | yes |
| 2-4% | 25 | 0.501 | 0.473 | 52.0% | yes |
| 4-6% | 13 | 0.532 | 0.481 | 30.8% | yes |
| 6-8% | 11 | 0.564 | 0.498 | 63.6% | yes |
| 8%+ | 19 | 0.527 | 0.419 | **31.6%** | yes |

**This is the sharpest finding in the study.** The lowest-disagreement
bucket (0-2%, effectively the PASS boundary) has the *best* actual win rate
(65.4%, n=26); the largest-disagreement bucket (8%+, the model's strongest
market-defiance) has one of the *worst* (31.6%, n=19), and win rate is not
monotonic but trends downward with increasing disagreement overall (65% ->
52% -> 31% -> 64% -> 32%, with 6-8% as the one exception at only n=11). This
directly answers the task's specific question -- **yes, the
largest-disagreement bucket underperforms** -- and is the same qualitative
pattern ML-013 found on the historical dev folds (calibration gap 5-7x
larger where the model diverges most from the opening market, both times
moving toward the market's own view). It reads as a possible
missing-information signal (the market often has information the model's
feature set doesn't -- late scratches, weather, bullpen availability, sharp
money) rather than pure classifier noise, though every bucket here is
individually low-confidence (n<30) and this needs more data to confirm.
ROI: not computed (no stake field, same reason as Part 2).

## 8. Part 5 -- failure regimes

Raw P(home_win) framing throughout (comparable to ML-013's own convention),
`edge_threshold=0.02`, `near_fifty_band=0.05`.

| dimension | buckets (n) | notable |
|---|---|---|
| favorite_underdog | home 51 / away 43 | model_favors_away actual win rate 37.2% vs model_favors_home 54.9% -- both low-N-adjacent, not flagged low_confidence, but a real split worth watching |
| home_away_outcome | home_win 44 / away_win 50 | sanity check only (metrics here are tautological by construction) |
| home_away_selection | away 67 / home 27 | **the selection layer picks away 2.5x more often than home** -- a real asymmetry; away-picks slightly outperform home-picks (47.8% vs 44.4%, both n<30 for home) |
| near_50_vs_confident | near_50 46 / confident 48 | no material difference (45.7% vs 47.9% win rate) |
| high_edge_vs_low_edge | high_edge_play 68 / low_edge_pass 26 | identical split to PLAY/PASS (Part 2); low_edge_pass metrics use raw-P framing here, not directly comparable to Part 2's selected-side numbers |
| starter_quality_regime | low 29 / mid 27 / high 33 | low_tercile (home starter has the better/lower ERA) wins 65.5%, mid_tercile only 29.6% -- large spread, all low-N, worth monitoring not concluding |
| bullpen_workload_regime | low 31 / mid 30 / high 33 | no material spread (42-53%) |
| time_to_first_pitch | <2h 36 / 2-6h 35 / 6-24h 23 | no material spread (41.7-52.2%) |

**Skipped cleanly, with stated reasons (not fabricated):**
- **sportsbook** -- the canonical journal is pinned to a single sportsbook
  (`the_odds_api:draftkings`, per PIPE-004); no cross-book variation exists
  in `daily.jsonl`/`journal.jsonl` to slice by.
- **starter uncertainty / missing-late-starter** -- games with no announced
  starter are excluded *upstream*, before a prediction row is ever written
  (`skipped.jsonl`, `reason=no_starter_announced`); by construction they
  cannot appear in the resolved-prediction set as a per-row slice.
  `starter_quality_regime` above is the nearest available proxy (ML-013's
  starter-ERA-differential tercile, not the same concept). The aggregate
  skip count is a data-quality note instead (Section 9).

## 9. Data-quality notes

- **5 games skipped for no announced starter** (`skipped.jsonl`,
  `no_starter_announced`) in this window -- expected upstream behavior
  (PIPE-003), not a defect.
- **0 malformed/skipped board rows** -- the daily board's own diagnostics
  found no schema problems in this window's `daily.jsonl`.
- **Duplicate same-game predictions are real, not a bug.** ~half of games in
  `daily.jsonl` were predicted more than once (once ahead of the slate, once
  closer to first pitch, as odds/features refreshed); this study dedups to
  the latest prediction per game before first pitch, matching the live
  board's own convention, so these are not double-counted. Most duplicate
  pairs carry an identical `model_probability` (the market snapshot moved,
  the model call didn't); a minority differ meaningfully, reflecting
  legitimate feature drift (e.g. rest days, recent bullpen usage) between the
  two prediction timestamps for the same game -- not re-inspected further
  here since it doesn't affect the analysis (only the final, latest
  prediction is used).
- **No genuine correctness defect found.** Nothing here rises to the
  P0/P1 leakage-style escalation bar this repo's ML-012/ML-013 tasks use --
  the model and pipeline are behaving as designed; the pattern found is a
  market/selection-layer signal, not a bug.
- The `journal.before-edge-side-fix.jsonl` backup file in
  `state/predictions/` (4 stale records from before the OBS-002 edge-side
  scoring fix, commit `93787ad`) predates all enrichment in the current
  `journal.jsonl` (enrichment starts 2026-08-14T14:15 UTC; the fix landed
  2026-08-14T07:15 UTC, same morning, before any enrichment ran) -- confirmed
  the current journal is entirely post-fix and this study never reads the
  stale backup file.

## 10. Historical comparison summary

Discrimination (ROC-AUC) is statistically indistinguishable from the locked
2026 holdout (-0.0024, n=94 vs. n=1,797). Log loss/Brier are mildly worse by
an amount comparable to the already-known dev-to-holdout gap, not a new
regression. Accuracy is better. The probability model, on its own raw
output, shows no sign of failure in its first week of live production data.

## 11. Final conclusion

**`MARKET/PLAY LAYER APPEARS MORE CONCERNING`**

Justification: Part 1 (all 94 resolved predictions, raw P(home_win)) shows
ROC-AUC essentially unchanged from the locked holdout and log loss/Brier
degradation in line with the already-documented dev-to-holdout gap -- no
evidence of a probability-model regression. Part 3's probability buckets
show no monotonic or concentrated calibration failure. In contrast, Part 4's
edge buckets show a real, directionally consistent pattern (lowest
disagreement performs best at 65.4%, highest disagreement performs worst at
31.6%, same qualitative shape ML-013 already found in historical dev-fold
data), and Part 2 shows the PLAY selection specifically underperforming
what simply following the model's raw favorite would have achieved over the
identical window (44.1% vs. 58.5%). Together these point at the
market-disagreement/selection layer -- not the underlying probability model
-- as the more concerning locus, consistent with this repo's own
`src/app/board.py` warning that PLAY/PASS is a synthetic display threshold
that has never been validated as a staking policy.

This conclusion is **hedged, not certain**: every slice supporting it is
individually below `LOW_N_THRESHOLD=30` (Part 2 n=68 is above threshold, but
the edge-bucket breakdown within it is not). It should be treated as a
strong hypothesis to monitor, not a settled finding, until more prospective
data accumulates.

## 12. Recommended measurements for the next 2-4 weeks

1. **Re-run this exact study** (`scripts/ml015_prospective_diagnostic.py`)
   weekly as the journal grows, watching specifically whether the edge-bucket
   pattern (Part 4) holds, strengthens, or washes out as N crosses the
   `LOW_N_THRESHOLD=30` per bucket -- this is the single most decision-useful
   number to track.
2. **Track PLAY win rate vs. raw-favorite win rate on the same window**
   side-by-side (Part 2 vs. Part 1's accuracy) -- if PLAY continues to
   underperform raw-favorite-following at growing N, that is much stronger
   evidence for a market/selection-layer issue specifically, not model
   quality.
3. **Watch `home_away_selection`'s 67/27 away/home split** for whether it
   persists or was a first-week artifact of this particular slate of
   matchups/odds.
4. **Do not retune, recalibrate, or change `DEFAULT_EDGE_THRESHOLD`** from
   this prospective sample alone, per this task's own constraint -- if the
   edge-bucket pattern holds at higher N, the right next step is a
   proposal/ADR for a staking-policy study on its own dedicated data, not a
   silent threshold change here.
5. Re-run the ROC-AUC/log-loss/Brier holdout comparison (Part 1) at larger N
   to confirm the current near-zero ROC-AUC delta and modest log-loss/Brier
   gap are stable, not early noise.

## 13. Known limitations

- N=94 total, N=68 PLAY, and every finer-grained slice below is small; this
  is explicitly a first-week monitoring snapshot, not a statistically
  powered study.
- `starter_quality_regime`/`bullpen_workload_regime` terciles are computed
  over this prospective sample's own 94 games (not ML-013's historical
  distribution), per this task's own instruction that literal fold reuse
  isn't possible for live data -- naming/threshold conventions match ML-013,
  but the tercile cut points themselves are this sample's own.
- `home_away_selection`'s raw-P-framing metrics in Part 5 are not directly
  comparable to Part 2's selected-side PLAY metrics, even though both
  describe overlapping games -- documented explicitly in Section 8 to avoid
  a mixed-framing misread.
- ROI is entirely absent (no stake/wager field exists in this repo's data)
  -- any future staking-policy work needs that field added first, not
  inferred here.
